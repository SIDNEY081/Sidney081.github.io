SmartGrid PredictAI

Predicting transformer failure, electricity theft, and feeder outages on a synthetic model of Eskom's distribution network

Live Demo Source Code

The problem

Eskom's distribution network runs on aging, unevenly monitored infrastructure, and three failure modes matter most operationally: transformers failing unexpectedly, electricity theft eating into revenue, and feeders going down. Each needs a different kind of detection - transformer failure has a paper trail of past incidents to learn from, theft is deliberately hidden so confirmed cases are rare and biased toward wherever someone already looked, and feeder outages depend partly on the health of the transformers sitting on that feeder. SmartGrid PredictAI treats these as three related but distinct prediction problems rather than one generic "risk score."

The data

Real Eskom data isn't available for a personal project, so the dataset is synthetic but schema-realistic: 3,000 transformers (capacity, installation year, previous failures, service/oil-replacement history, GPS location, plus 12 months of oil-quality/temperature/load readings per unit), 10,000 meters (~10% flagged theft), and 500 feeders (age, vegetation encroachment, protection-equipment age, load, historical outages). Every asset carries substation and feeder relationships so the data behaves like a real grid hierarchy, not disconnected rows.

Model choices, and why

Transformer Failure

Random Forest · ROC-AUC ≈ 0.86

Supervised - Eskom-style data has labeled history of transformers that actually failed, with sensor readings leading up to the event. Random Forest handles mixed-scale tabular features well and its probability output converts directly into a risk tier.

Electricity Theft

Isolation Forest · ROC-AUC ≈ 0.98

Unsupervised - confirmed theft cases are rare and biased toward wherever someone already investigated, so a classifier trained on them would just learn "where we've looked before." Isolation Forest flags statistical outliers in consumption instead. The strongest engineered feature: the ratio between what a transformer fed a connection and what the meter declared - a classic bypass/tampering signature.

Feeder Outages

Gradient Boosting · ROC-AUC ≈ 0.75

Supervised, using each feeder's own condition plus emergency_transformer_count - how many transformers already flagged "emergency" by the failure model sit on that feeder. It's the one place the three models actually talk to each other: a feeder carrying several already-risky transformers is a more plausible near-term outage than one judged on its own attributes alone.

An honest weak spot: feeder outages

0.75 ROC-AUC is clearly the weakest of the three, and it's expected to stay that way even with more synthetic feeders. The gap is missing real-world signal this dataset doesn't model - weather, live vegetation growth, crew response time - not a sample-size problem a bigger dataset would fix. Stating that honestly in the README mattered more than tuning the number up artificially.

Explainability, not just a score

Every scored row gets a plain-language reason via SHAP's TreeExplainer (e.g. "high age_years, low oil_quality_index, high load_factor"), with a dependency-free z-score fallback if SHAP isn't installed. A risk score without a reason isn't something a maintenance planner can act on with confidence.

From notebook to product

The models feed two live surfaces. A Flask dashboard sits behind real authentication - password hashing, server-side sessions, and four SQLite-backed roles (Administrator, Maintenance Engineer, Revenue Protection Officer, Field Technician), each enforced server-side on every route, not just hidden nav items - so an engineer sees transformer/feeder risk while an investigator sees meter theft, matching how the work is actually split. A Streamlit console covers the same three models with SHAP charts for anyone who just wants to explore the data, no login required. Both export directly into Power BI / Tableau - via CSV or, for Power BI Service, a live authenticated API endpoint - with an ordinal severity column so BI tools sort by risk instead of alphabetically.

An AI assistant that can't make numbers up

The dashboard's AI Assistant tab uses Claude with real tool access rather than free-text generation: every reply function (predict, health, history, compare, generate-report) is wrapped as a typed tool, and the model's job is understanding the question and phrasing the answer - every fact it states comes from an actual tool call against the scored CSVs, never from memory. If no API key is configured, the tab says so plainly instead of failing silently.

Keeping it honest

The failure and theft pipelines are deliberately implemented twice - once as notebooks, once as standalone scripts - and kept independent rather than sharing code, because duplicated logic was exactly what caused earlier schema-drift and inflated-metric bugs in this project. A pytest suite now specifically checks for that class of bug: data files still matching what the models expect, no filename collisions between notebook and script outputs, and every capacity-based alert flag firing at roughly its intended rate. Two fields are labeled explicitly as heuristics rather than real statistics - confidence_pct (distance from a 50% decision boundary, not model uncertainty) and remaining_useful_life_years (a rule-of-thumb estimate, not a survival-curve model) - because a number that looks precise but isn't is worse than an honest approximation.
